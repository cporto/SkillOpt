## Learned preferences & procedures

_This block is maintained by SkillOpt-Sleep. Edits here are proposed offline, validated against your past tasks, and adopted only after you approve them. Hand-edits outside this block are never touched._

- When comparing AI models for cost-effectiveness, always include columns for Intelligence and Coding metrics in the comparison table.
- In any report containing token usage statistics, always calculate and display the dollar cost of tokens used and provide a summary of changes compared to the previous period.
- The daily Inference Optimization Watchdog report must start with exactly the heading '## 🔍 Inference Optimization Watchdog — YYYY-MM-DD' and contain no preamble before it.
- When I request a list of local businesses (e.g., movers, plumbers), respond with the actual list containing at least a direct link (website or Google Maps) and a phone number for each entry; do not merely state an intention to include them.
- When you indicate that you will perform an action (e.g., testing an alternative backend, running a script, checking service health), you must actually execute that action and report the outcome; never respond with only a statement of intent.
- When performing a system health check that requires specific identifiers (e.g., port numbers, LaunchAgent labels, conflicting service registrations), attempt to discover these identifiers from the running system using appropriate commands (e.g., lsof, launchctl list, systemctl) before asking the user; only ask if automated discovery fails.
- When asked to save notes, meeting summaries, or analysis to a wiki, save them immediately without asking for content. Use a descriptive, hyphenated filename (e.g., 'meeting-project-alpha-2025-03-15') and place the file in the 'con' directory. If the exact content is ambiguous, extract it from the preceding conversation; only ask for clarification if no relevant content exists anywhere in the context.
- When asked to set a follow-up reminder based on conversation context, explicitly confirm the reminder is set with the specific date and time. Extract the date, time, and subject from the conversation; if any of these are genuinely missing and cannot be inferred, state exactly which piece is missing. Never respond with 'I can't set a reminder' without first attempting to extract all necessary details from the available context.
- At the end of every work session, include a bullet-point summary checklist of completed action items. The checklist MUST start with a clear summary header (e.g., '## ✅ Completed Action Items') and each item MUST be prefixed with a checkmark emoji (✅ or - [x]). This checklist must appear as the final section of the response.
- When provided with a video or YouTube link, you MUST extract and produce an actual summary, a list of actionable items, and a catalog of referenced resources (links to tools, skills, etc.) from the video content. Never respond with only an empty template or a request for the URL if the URL is already present in the context. Use available tools to access and analyze the video content directly.
- OVERRIDE: When a request asks to extract key actionable points or notes from a YouTube/video link, save those points as concise notes to the wiki under `concepts/` (this supersedes any general rule to save wiki files in `con`). Never respond with only a template or ask for the URL if the URL is already present in the context.
- OVERRIDE: When asked to set a reminder and the conversation contains a specific day and time (or they are clearly inferable), set the reminder immediately and confirm it is scheduled with the exact day and time in the response. Only ask for missing details if the day, time, or subject is genuinely absent and cannot be inferred; never re-ask for details already provided.
- When a user request asks for a concrete output (e.g., a list, a summary, a script, a status update), respond with that output directly. Do not respond with a statement that you cannot produce it because information is missing; instead, use the available context and make reasonable assumptions, clearly noting any assumptions you make.
- If a user message contains a command phrase (e.g., 'list', 'summarize', 'create', 'chunk', 'provide', 'update'), treat it as an instruction to perform that action immediately. Never ask for clarification; infer missing details from the conversation history. If you cannot infer, state that you are making an assumption and proceed.
- When a task references content that is not explicitly provided in the current message (e.g., 'the text', 'my notes', 'the conversation'), use the most recent relevant content from the conversation. If none exists, provide a partial response or a template, but never respond with only a request for that content.
- For any request that implies a deliverable (such as a status report, a list of businesses, or a script), your response must include the deliverable itself. Never respond with only a statement of readiness or a request for more information.
- When reporting any change you applied (fix, commit, file edit, deploy), always provide the actual, concrete identifiers in your response: real branch name, commit hash, PR number, file path(s), and service state. Never output placeholder tokens such as `<branch>`, `<commit>`, `<PR>`, `<file path(s)>`, or `<running/stopped/degraded>`. Obtain these values from your executed commands; if a value is genuinely unavailable, say explicitly which value is missing and why.
- When diagnosing a service problem (e.g., unreachable, blank page, failed restart, or hang), you must run and report actual diagnostic commands and their outputs: include the exact command, the returned exit code or key log lines (e.g., `systemctl status <service>`, `journalctl -u <service> -n 50`, `curl -I http://localhost:<port>`, `ps aux | grep <process>`). Never answer with a generic troubleshooting checklist or unverified assumptions; quote the evidence from the live system.
- When asked to harden or fix a component, you must (a) identify at least one specific edge case or fault path, (b) describe the exact change you will make (code, config, or command), (c) apply that change, and (d) verify it with a concrete check (e.g., re-run the failing scenario, check exit code, or confirm new status). Never respond with only a general preference or an intention to fix; deliver the actual fix and its verification in the same turn.
- When given a video or YouTube link in the current context, you must produce an actual summary, a list of actionable items, and a catalog of referenced resources by using available tools to access the video content. Never use placeholders like '[video title]' or 'not provided' when the URL is present. If audio/transcript extraction fails, report that failure and include the raw link, then provide the best-available extractable content (e.g., title, description, timestamps).
- When you state that you will validate a proposed fix with a fusion session or parallel subagents, you must actually run that validation in the same turn before finalizing the fix, and report the outcome: the number/roles of participants, their consensus or disagreements, and the adjustment you made as a result. Never end with only a statement of intent to validate.
- When investigating a recurring background-service or auto-update failure, gather and quote real evidence from the live system (e.g., `launchctl list`, `systemctl list-units --failed`, `journalctl -u <service> -n 50`, relevant log file lines, or `ps aux`) before or as part of the fusion session; identify the root cause from that evidence, implement a durable fix, and verify it with a concrete check. Do not rely on explicit assumptions as the basis for root cause; if a service name or log is not in the prompt, discover it from the system and explicitly list what was found and what was missing.
- When rebuilding failed or corrupted launchd jobs, your report must list the specific dead/failed job labels (e.g., from `launchctl list | grep -v com.apple` or `launchctl print-disabled`), state the rebuild command used for each label, and then verify each is running again with `launchctl print <label>` or `launchctl list` output. Never give a launchd rebuild report that omits the specific dead/failed jobs.
- Never reply 'No task was provided' when the user's message states a desired outcome (e.g., 'Coordinate service reboots with update windows to avoid redundant restarts'). Treat that outcome as the task, infer the implied steps, and produce the deliverable in the same turn.
- For any requested operational coordination with constraints (e.g., reboots/restarts, maintenance/update windows), always explain how you would discover the relevant current state (pending updates, service status, schedule) and how you would adjust/sequence actions to satisfy the constraint (e.g., wait for/batch within the window to avoid redundant restarts). If exact details are absent, state explicit assumptions and proceed; do not stop at missing information.
- When planning service restarts, avoid redundant restarts by first checking for pending updates/reboot requirements. If an update is pending, defer or batch the restart into the update/maintenance window, and report the check performed and the timing decision.
- When determining whether a background runner is executing, output a verdict line 'RUNNING: YES' or 'RUNNING: NO' followed by evidence bullets for ALL of memory, lockfile, preflight, and baseline; quote the actual value/command/output for each (use 'NONE' or 'NOT CHECKED' if absent). Do not report only 'no background runner is confirmed' without this structured evidence.
- When asked to validate or refute a claimed root cause from a provided brief/code, state a verdict ('VALIDATED', 'REFUTED', or 'PARTIALLY SUPPORTED') as the first sentence, quote the concrete code lines/logs supporting it, and propose a minimal safe fix design (file/function/change). Do not reply with a request for the diagnosis or code if any relevant snippet exists in context; if nothing exists, say exactly which input is missing.
- When analyzing a WebUI code path to conclude a root cause, explicitly trace and evaluate the active code path under the user's current custom chat activity display mode (e.g., transparent_stream mode) and state whether the bug reproduces in that mode. Do not respond with advice to account for the mode without performing that evaluation.
- For any UI comparison request, you must actually use the requested reasoning skill (e.g., Fable) AND computer-use/vision to inspect the screenshots or UI elements present in the context, and quote the analysis output in your response. Never reply with only 'I will use X' or 'no screenshot provided' without first attempting to extract visual data from the context (e.g., images, links). If no visual data is available, state exactly which input is missing and provide a partial analysis based on any textual description.
- For any request to conduct a fusion review of skill recommendations, you must actually run a fusion session (real or simulated) and report the number of participants, their consensus/disagreements, and any adjustments. If no recommendations are supplied in context, you must state that explicitly and then propose a minimal set of candidate recommendations based on the reasoning in the request, or outline the evaluation criteria. Never respond with only 'No skill recommendations were supplied' as the entire response.
- When continuing an existing development project, before making any changes, list the outstanding tasks/remaining work as a bullet-point enumeration, each item referencing the relevant file, function, or issue if identifiable. Then perform the changes and report what you did. Never simply state 'I will summarize outstanding work' without actually listing the tasks.
- When restoring a feature from an older git commit, you must first run git commands to determine the target commit, current HEAD, and the affected files (e.g., `git log --oneline`, `git diff HEAD <target> -- <file>`). Report these concrete identifiers (commit hashes, branch names, file paths) in your response. If the repository is not present, attempt to discover it (e.g., `git status`); only if no repository exists, state exactly what is missing. Never reply 'no repository/commit present' without running `git` commands.
- When asked to finish existing work and commit it, run `git status`, `git log --oneline -5`, and inspect the working tree for remaining/unfinished changes before answering. Complete that remaining task, commit it, and report the actual commit hash (`git rev-parse HEAD`) plus changed file paths. Do not claim 'no pending work' or 'no repository' without quoting the output of these discovery commands.
- When a user reports issues with a named pipeline/service, fix all of them end-to-end in the same turn: locate the relevant code/config, apply fixes, and verify the previously reported issues are resolved with quoted evidence. Do not respond with only a protocol/plan or request for the report when the issues are already stated in context.
- Before reporting a fix as complete, reproduce the original failing scenario in the same turn, apply the fix, and quote the actual verification output (exit code, test result, or log lines) showing the scenario now passes. A statement of intent such as 'I will reproduce, apply, and verify' or 'verified ✅' without quoted evidence is not completion.
- When evaluating an external article or repository against an internal model or test-selection criteria, run an actual empirical test (execute the relevant code/benchmark/script) and quote the resulting output in your response; restating the rule without evidence is not an evaluation. If an executive summary of a completed test/analysis is requested, include the four required elements — what was done, what was tested, the results, and the final decision — based on that real work; never label it 'illustrative', 'simulated', or 'no details present'.
- OVERRIDE: When re-deriving a design from a brief and evaluating proposed implementations, never fabricate specific file names, line numbers, code snippets, or commit hashes. If a concrete identifier (file path, line number, commit hash) is not verifiable from the actual code in context or from executed commands, state explicitly 'UNVERIFIED: [identifier]' next to it and distinguish verified claims (quoting actual code/log lines) from unverified ones. Never present invented specifics as facts; if no real code is available, say exactly which code input is missing.
- OVERRIDE: When analyzing implementation choices (e.g., ID generation location, indexing scope) for a design brief, always structure the response as: (1) For each alternative, list at least two concrete trade-offs (one pro, one con) and a clear recommendation, (2) a final decision paragraph that explicitly states which alternative you chose for each choice and why, (3) a 'Trade-offs Compared' subsection that quotes the specific criteria from the brief or code. Never omit the final decision or present only a table without the concluding recommendation.
- OVERRIDE: When diagnosing gateway or API server issues (e.g., 502, service conflicts, bind races), your response MUST include a verdict line 'DIAGNOSIS: [CONFIRMED/REFUTED/PARTIAL]' as the first sentence, followed by at least three distinct evidence subsections: 'Conflict Detection' (quoting `lsof -i :<port>` or `/proc/net/tcp`), 'Bind Race Analysis' (quoting the start sequence or log timestamps), and 'Failed API Response' (quoting the actual 502 body or `curl -I` exit code). For each subsection, quote the real command output; if a check was not possible, write 'NOT CHECKED — reason'. Never produce a generic checklist without actual diagnostic evidence.
